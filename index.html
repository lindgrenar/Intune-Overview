Intune & Entra ID

Every object in the targeting chain with its properties absorbed as facets. Identity produces group membership → groups (refined by filters) drive assignment → assignments push workloads to managed devices → compliance verdict gates Conditional Access. Scope tags and RBAC are admin-plane overlays: they do not touch device targeting.

A2 · ENTRA USER
User

Cloud or AD-synced identity. Drives user-targeted assignments and sets primary-user affinity on enrolled devices.

Attributes read by dynamic rules
  • Department · city · country · job title
  • userPrincipalName · mail · extensionAttribute1–15
Carries
  • Licenses: Intune Plan 1 · Plan 2 · EMS E3/E5 · M365 E3/E5
  • Entra ID P1 (Conditional Access) · P2 (risk-based CA)
  • Primary-user link to managed device
A3–A4 · ENTRA DEVICE
Entra Device

Identity record for an enrolled endpoint. Two representations exist simultaneously: this Entra object and the Intune managedDevice record.

Entra Registered
  • BYOD path; no local Entra sign-in on Windows
  • CloudAP authenticates per-app; MDM-enrollable or MAM-only
Entra Joined
  • Cloud-native corporate Windows; local Entra sign-in (WAM)
  • Auto-enrolls in Intune MDM; supports Autopilot · WHfB
Entra Hybrid Joined
  • Domain-joined + synced via Entra Connect
  • On-prem AD primary authority; SCP points device to Entra tenant
  • Requires DC line-of-sight post-OOBE for full functionality
Key attributes
  • deviceId · trustType · enrollmentProfileName
  • devicePhysicalIds: [ZTDId]:… · [OrderID]:<tag>
  • isCompliant — written by Intune, read by Conditional Access
  • MS-Organization-Access cert (10 yr) · Primary Refresh Token (PRT)
E1 · AUTOPILOT DEVICE
Autopilot Device

Pre-registered hardware record in the Autopilot service. Exists before the device is ever powered on; uploaded by OEM, reseller, or IT via CSV or Graph API.

Identity
  • Hardware hash · serial number · manufacturer · model
Group tag
  • Free-text field set at device hash upload
  • Stored as [OrderID]:<tag> in devicePhysicalIds
  • Matched in dynamic group: device.devicePhysicalIds -any "[OrderID]:Sales"
  • No effect without a dynamic group and profile assignment
ZTDId
  • Autopilot-unique device identifier; auto-generated at upload
  • Stored as [ZTDId]:…; also matchable in dynamic rules
  • Resolves to enrollmentProfileName after profile assignment
A6 · SECURITY GROUP
Security group

The universal targeting container. Every Intune assignment points at one — or at the virtual All users / All devices built-ins.

Assigned membership
  • Users / devices added manually or via Graph API
  • Owners list with group-management permissions
Dynamic rule
  • KQL-style query; re-evaluated as objects change
  • Device keys: devicePhysicalIds · enrollmentProfileName · deviceCategory · deviceOSType · deviceTrustType
  • User keys: department · jobTitle · accountEnabled · extensionAttribute*
Assignment intent
  • Include vs. Exclude group precedence (Exclude always wins)
  • Mixed targeting (e.g. Include User Group + Exclude Device Group) introduces evaluation latency and unpredictability
Also used for
  • Conditional Access user scoping
  • Entra ID role assignment (role-assignable groups only)
  • License assignment · AU membership
A7 · ADMINISTRATIVE UNIT
Administrative Unit

Entra virtual container limiting the reach of directory roles to a subset of users and devices. Paired with Intune scope groups for distributed IT teams.

Variants
  • Standard AU: scopes Entra roles to a subset of objects
  • Restricted Management AU (RMAU): blocks non-scoped admins from modifying members
Typical pairing
  • AU narrows Entra role (e.g. Intune Administrator) to regional users/devices
  • Scope group narrows Intune RBAC role assignment
  • Scope tag restricts object visibility in Intune portal
D7 · ASSIGNMENT FILTER
Assignment filter

Per-assignment include / exclude rule over device properties. Evaluated at every device check-in — not at group-membership time. Preferred over dynamic groups for device-only targeting: no membership-sync latency.

Device properties available
  • operatingSystemSKU · osVersion · osBuildVersion
  • manufacturer · model · cpuArchitecture
  • deviceOwnership: personal · corporate
  • deviceCategory · enrollmentProfileName
  • deviceManagementType
Limits
  • 200 filters per tenant · 3 072 chars each
D5 · POLICY SET
Policy set

Assignment bundle. Groups apps, configuration profiles, compliance policies, Autopilot profiles, and app protection policies into one assignable object. Assignment convenience only — no effect on what contained objects do.

Can contain
  • Apps (all types) · App configuration policies
  • Device configuration profiles · Compliance policies
  • Autopilot deployment profiles · ESP profiles
  • App protection policies
D1–D2 · RBAC
RBAC roles & assignments

Controls what admins can do in Intune. Entra roles (Intune Administrator · Global Administrator) override Intune RBAC entirely.

Built-in roles
  • Policy & Profile Manager · Application Manager
  • Help Desk Operator · Read Only Operator
  • Endpoint Security Manager · Intune Role Administrator
Role assignment binds
  • Role + admin security group + scope groups + scope tags
  • Multi-Admin Approval: workflow for policy create / edit / assign
D3 · SCOPE TAG
Scope tag

Free-form label on Intune objects controlling which admins can see and edit them. Zero effect on device targeting. Every tenant has a Default tag visible to all admins.

Applied to
  • Config profiles · compliance · endpoint security
  • Apps · scripts · remediations · baselines
  • Autopilot devices and profiles · ESP profiles
E · WINDOWS ENROLLMENT
Windows enrollment

How a Windows device becomes managed. Autopilot is the zero-touch path; all variants perform an Entra join during OOBE.

Autopilot deployment profiles
  • User-driven (Entra join) — user signs in at OOBE; device imprints to that user
  • User-driven (Hybrid join) — Entra join + domain join; requires post-OOBE DC line-of-sight
  • Self-deploying — no user credentials at OOBE; userless / shared / kiosk
  • Pre-provisioned (white-glove) — IT pre-stages; user completes second phase
Autopilot device preparation profile
  • Newer model; assigned to user group (not device group)
  • Enrollment-time grouping: device added to Entra group during enrollment; policies and apps apply inside ESP
  • Supports Win32 + LOB apps in ESP; classic Autopilot supports LOB only
Enrollment Status Page (ESP)
  • Two-phase: device setup (pre-login) + user setup (post-login)
  • Blocks desktop until required apps / profiles are installed
  • Settings: allow use on error · allow reset · custom error message · timeout
Other enrollment objects
  • Device categories: User prompt in Company Portal writes category to Intune record → syncs to Entra → drives dynamic grouping
  • Enrollment restrictions: platform · OS version range · device limit (1–15) · manufacturer
  • Bulk enrollment: Windows Configuration Designer (.ppkg) · DEM account (≤1 000 devices)
  • Corporate identifiers: pre-imported IMEI / serial — flips ownership to corporate
  • MDM/MAM auto-enrollment scope: Entra ID Mobility scope group triggers auto-enroll on Entra join
H · CONFIGURATION
Configuration

Settings, scripts, and update policies pushed via the MDM channel or Intune Management Extension (IME). Continuous — re-evaluated at every check-in.

Profile types
  • Settings catalog — recommended forward path; Administrative Templates deprecated Dec 2024
  • Templates: Device restrictions · Endpoint protection · Wi-Fi · VPN · Email · Kiosk · Shared multi-user device · Domain join · Edition upgrade · Custom OMA-URI
  • Group Policy analytics: import GPO XML → map to MDM CSP coverage → migrate supported settings to Settings Catalog
Code on device (via IME)
  • Platform scripts: PowerShell — runs as System or User context; output captured in admin center
  • Remediations: detection + remediation script pair; scheduled hourly / daily / once; output in admin center reports
Windows updates (via Autopatch)
  • Update rings: WUfB quality/feature deferral · service channel · pause up to 35 days
  • Feature update policy · Quality update policy · Driver update policy
  • Windows Update client policies (Settings Catalog category)
K · APPS
Apps

Software delivery. Each app has a type, an intent, and a context. Companion policies configure and protect the app after installation.

Windows
  • Win32 .intunewin: detection rules · requirement rules · dependencies (≤100) · supersedence · install context (user / system / dual) · restart behaviour · 30 GB max
  • LOB: .msi · .appx · .msixbundle (8 GB max)
  • Microsoft Store app (new): user/device context · auto-updates
  • Microsoft 365 Apps: C2R · channel · architecture · shared-computer activation
  • Enterprise App Catalog (Suite): 3 000+ prepackaged Win32 apps with auto-update
Companions
  • App configuration policy: managed devices (MDM/OS channel) or managed apps (MAM/SDK channel)
  • Intents: Required · Available (enrolled) · Available (with or without enrollment) · Uninstall
J · ENDPOINT SECURITY
Endpoint security

Purpose-built profiles for the device security stack. May overlap settings in Configuration; conflicts resolve per-setting — last write wins.

Profiles
  • Antivirus: Defender AV · exclusions · Windows Security UX · Defender Update controls
  • Disk encryption: BitLocker (Windows) — key escrow to Entra ID; rotation via remote action
  • Firewall: Windows Defender Firewall with per-rule profiles
  • EDR: onboards Defender for Endpoint; package type Auto (from connector) or manual blob
  • Attack Surface Reduction: ASR rules · Exploit protection · App & browser isolation · Web protection · Device control · Controlled folder access
  • Account protection: Windows Hello for Business · Credential Guard · LAPS (local admin password solution) · local user group membership
  • App Control for Business (formerly WDAC): code integrity policy · managed installer support
  • Endpoint Privilege Management — EPM (Suite): elevation settings + elevation rules (file / hash / publisher); behaviors: Automatic · User-confirmed · Support-approved
Security baselines
  • Windows (v24H2) · Defender for Endpoint (v24H1) · Edge (v128)
  • Microsoft 365 Apps (v2306) · HoloLens 2 Standard + Advanced (v1)
I · COMPLIANCE
Compliance policy

Health and risk rules evaluated on the device. The output — isCompliant — is written to the Entra device object and consumed by Conditional Access.

Rule sources
  • OS version range · password / PIN complexity · encryption (BitLocker)
  • Defender machine risk score: Clear · Low · Medium · High (via connector)
  • Firewall · antivirus · secure boot · code integrity · BitLocker
  • Custom compliance: PowerShell discovery script + JSON settings definition
Tenant settings
  • Validity period: 1–120 days (default 30)
  • Devices with no policy assigned: mark Compliant or Not compliant
  • Actions for noncompliance: email · push notification · remote lock · retire
K8 · APP PROTECTION (MAM-WE)
App protection · MAM

Side path. Identity-bound; enforced by the Intune App SDK inside the app. Works on unenrolled Windows PCs — the primary BYOD data-protection mechanism for Windows. Targets user identity, not device record.

Windows scope
  • Applies to Microsoft Edge for Business on unenrolled Windows 10/11 PCs
  • MAM-WE (without enrollment) — no MDM channel involved
  • Other Win32 apps require the device to be enrolled; MAM-WE scope is narrower than mobile
Data protection
  • Cut / copy / paste restrictions between work and personal contexts
  • Org data wipe on sign-out · selective wipe action from admin center
  • Encryption of org data at rest inside the managed app
Access requirements
  • PIN · work-account credentials · Windows Hello
Conditional launch
  • Min OS version · Defender threat level · offline grace period · disabled account check
O · CERTIFICATES & PKI
Certificates & PKI

Certificate delivery to managed devices for 802.1X, VPN, email signing, and client auth. Requires connectors to on-prem or cloud CA infrastructure.

Profile types
  • Trusted certificate: root / intermediate CA .cer to device trust store; required before SCEP/PKCS on non-Windows
  • SCEP: device generates CSR; validated via Certificate Connector + NDES; SID extension for strong cert mapping; subject/SAN variables (CN={{UserName}} · URN:UUID:{{DeviceID}})
  • PKCS: server-side key gen; Certificate Connector exports PFX to device
  • Imported PKCS: bulk-imported PFX for S/MIME signing; same cert to multiple users
Infrastructure
  • Certificate Connector for Microsoft Intune: on-prem Windows service; NDES bridge · PKCS issuance · PFX import · revocation reporting
  • NDES (AD CS role): fronts SCEP; published via Entra App Proxy; Intune NDES module rejects non-Intune requests
  • Cloud PKI (Suite): cloud-hosted CA; chains to customer root or Microsoft-issued root; replaces NDES + connector
Q1 · MANAGED DEVICE
Managed device

The enrolled endpoint. Two records, one physical device — Intune writes the compliance verdict back to the Entra device twin.

Entra device
  • Join type · trustType · owner
  • isCompliant — read by Conditional Access
  • MS-Organization-Access cert · PRT
  • devicePhysicalIds (group tag · ZTDId)
Intune managedDevice
  • Enrollment type · primary user · device ownership
  • Applied profiles · encryption status · jailbreak status
  • Compliance details · last check-in · device category
Co-management
  • SCCM + Intune dual authority on the same device
  • Workload sliders act as hard gates for Intune payload execution
Local execution
  • MDM channel: CSPs (settings · restrictions · Wi-Fi · VPN · certs)
  • IME: Win32 apps · scripts · remediations (Windows)
  • Intune App SDK: MAM policy enforcement inside apps
Remote actions
  • Sync · Restart · Wipe (selective / full) · Retire · Fresh Start
  • Autopilot Reset · BitLocker key rotation · LAPS key rotation
  • Remote lock · Reset passcode · Collect diagnostics
  • Remote Help (Suite) · Quick / full Defender scan
P · DEFENDER FOR ENDPOINT
Defender for Endpoint

Connected peer service — not part of Intune. Exchanges risk signals and tasks via the Defender connector (service-to-service, configured in Intune admin center).

Receives from Intune
  • EDR onboarding blob (via EDR endpoint security policy or config profile)
  • AV · Firewall · ASR · Account protection policies (Endpoint Security workload)
Sends to Intune / Entra
  • Machine risk score (Clear · Low · Medium · High) → consumed by Intune compliance policy and MAM conditional launch
  • Security tasks (Vulnerability Management → Intune admin queue; accept/reject; close loop)
Additional integration
  • Security management for MDE: Intune endpoint security policies delivered to Defender-managed devices not enrolled in Intune MDM
  • Defender app on Windows: native client; receives policy via MDM or security management
B1 · CONDITIONAL ACCESS
Conditional Access

Entra access gate evaluated at sign-in and continuously. Lives in Entra ID — not Intune. Final enforcement point for the compliance verdict.

Grant controls (endpoint)
  • Require device marked compliant
  • Require Entra hybrid-joined device
  • Require app protection policy (MAM side path)
  • Require authentication strength
Targeting & Filtering
  • Filter for devices: Entra ID rule evaluated at auth time (distinct from Intune check-in filters)
  • Scopes: User groups · cloud apps · network locations
Enforcement
  • Sign-in evaluation: Reads isCompliant, risk score, and MAM status
  • Continuous Access Evaluation (CAE): Immediately revokes active session tokens if compliance is lost
